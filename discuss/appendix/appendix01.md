这是一个典型的 **"Heavy Logic in Rust, Reactive UI in Flutter"** 的混合架构。

---

### 1. 核心架构哲学：职责分离 (Separation of Concerns)

在 FRB 项目中，最大的陷阱是"逻辑泄露"——即在 Flutter 层做了太多计算，或者在 Rust 层处理了太多 UI 状态。

#### **Rust 层 (The Engine)**
*   **定位**：无状态的计算引擎 + 持久化存储管理器。
*   **核心职责**：
    1.  **资源解析与标准化**：将 EPUB 的非结构化/半结构化数据（HTML/CSS/OPF）转化为结构化的、易于分页的中间表示（IR, Intermediate Representation）。
    2.  **分页算法**：这是最重的计算部分。根据视口尺寸、字体设置、行高，计算出"哪些内容块属于哪一页"。
    3.  **资产管道 (Asset Pipeline)**：图片的解码、缩放、格式转换（如转 WebP）、哈希计算。
    4.  **缓存管理**：基于 `sled` 的 KV 存储，管理分页结果和图片缓存。利用 `config_hash` 实现自动失效。
*   **特点**：纯函数式倾向，输入确定，输出确定。不关心"当前显示第几页"，只关心"给定条件，第 N 页是什么"。

#### **Flutter 层 (The View & State)**
*   **定位**：响应式 UI 渲染器 + 交互状态管理器。
*   **核心职责**：
    1.  **视口感知**：获取屏幕尺寸、DPI、用户设置的字体大小。
    2.  **状态同步**：使用 `signals_flutter` 管理当前页码、加载状态、错误状态。
    3.  **虚拟列表/页面构建**：根据 Rust 返回的页索引，请求对应的内容块。
    4.  **异步资源加载**：接收 Rust 返回的图片路径（或字节流），在 Widget 树中展示。
*   **特点**：声明式 UI，关注"如何展示"和"用户交互反馈"。

### 2. 数据流设计：从 EPUB 到像素

我们需要定义一条清晰的数据流水线，避免在内存中重复持有大量数据。

#### **阶段一：解析与索引 (Parsing & Indexing)**
*   **输入**：EPUB 文件路径。
*   **过程**：
    1.  Rust 解压 ZIP，读取 `content.opf` 建立资源清单。
    2.  解析 HTML 文件，提取文本节点和图片引用。
    3.  **关键点**：此时**不进行分页**。只生成一个扁平的"内容流"（Content Stream）。
    4.  将内容流的元数据（章节 ID、总字数、图片数量）存入 `sled`，建立快速索引。
*   **输出**：轻量级的元数据结构，用于快速跳转章节。

#### **阶段二：按需分页 (On-Demand Pagination)**
*   **触发**：用户打开某一章，或改变字体大小/屏幕方向。
*   **过程**：
    1.  Flutter 传递当前视口参数（Width, Height, FontSize）给 Rust。
    2.  Rust 检查 `sled` 中是否存在该配置下的分页缓存（Key: `chapter_id + config_hash`）。
    3.  **Hit**: 直接返回分页索引列表（每页包含的内容块 ID 范围）。
    4.  **Miss**: 执行分页算法，生成索引列表，写入 `sled`，然后返回。
*   **优化策略**：分页结果不应该包含具体的文本字符串或图片二进制数据，只包含**引用 ID** 和**布局元数据**（如图片宽高比）。这样缓存极小，查询极快。

#### **阶段三：资源渲染 (Resource Rendering)**
*   **触发**：Flutter 构建某一页的 Widget 时。
*   **过程**：
    1.  Flutter 拿到内容块列表。
    2.  遇到文本：直接渲染。
    3.  遇到图片：调用 Rust 的 `get_processed_image(image_id, target_width)`。
    4.  Rust 检查图片缓存，处理后返回本地文件路径。
    5.  Flutter 使用 `Image.file()` 加载。

### 3. 缓存策略：多层级与失效机制

你提到的 `config_hash` 和 `sled` 是这里的核心。

#### **缓存层级**
1.  **L1: 内存缓存 (Optional)**：如果频繁切换前后页，可以在 Rust 层用 `DashMap` 或 `LRUCache` 缓存最近 5-10 页的布局结果。但这会增加内存压力，需权衡。
2.  **L2: 磁盘分页索引 (Sled)**：存储 `PageInfo` 结构。由于只存 ID 和坐标，体积很小，适合长期持久化。
3.  **L3: 磁盘图片缓存 (Sled + File System)**：
    *   `Sled` 存映射关系：`image_id + hash -> file_path`。
    *   `File System` 存实际的处理后图片文件。

#### **失效机制 (Invalidation)**
*   **配置变更**：当用户修改字体、行距、页边距时，更新全局 `config_hash`。所有依赖旧 hash 的分页索引自动失效（因为 Key 不匹配了）。
*   **内容变更**：如果 EPUB 文件被替换，更新 `epub_file_hash`。
*   **图片变更**：通常 EPUB 内图片不变，但如果支持在线更新图片，需单独维护图片版本的 hash。

### 4. 关键技术挑战与解决方案

#### **挑战 A：异步与阻塞**
*   **问题**：分页算法是 CPU 密集型，图片处理是 I/O + CPU 密集型。如果在 FRB 的主线程同步调用，会卡死 Flutter UI。
*   **架构解法**：
    *   FRB 默认支持异步桥接。确保 Rust 侧的分页函数标记为 `async` 或在后台线程池执行。
    *   **预取策略 (Prefetching)**：当用户在第 N 页时，Rust 后台静默计算 N+1, N+2 页的分页索引和图片预处理。这需要将"计算任务"和"UI 请求"解耦。

#### **挑战 B：图文混排的复杂性**
*   **问题**：简单的"文本一行行排，图片一个个插"无法处理 CSS Float、Inline-block 等复杂布局。
*   **架构取舍**：
    *   **方案 1 (简化版)**：限制 EPUB 的 CSS 支持。只支持块级元素和基本内联样式。图片强制为块级或简单的内联。这在技术书籍或小说阅读器中是可接受的。
    *   **方案 2 (完整版)**：集成一个轻量级 HTML 布局引擎（如 `servo-stylo` 的裁剪版，或自研简化的 Box Model 实现）。这会显著增加 Rust 层的复杂度。
    *   **建议**：对于大多数阅读器，**方案 1** 足够。通过预处理 HTML，将复杂的 CSS 转换为简单的样式属性，再交给 Rust 分页。

#### **挑战 C：内存管理**
*   **问题**：EPUB 可能包含高清大图，全部加载到内存会 OOM。
*   **架构解法**：
    *   **零拷贝思想**：Rust 处理图片后，直接写入文件系统，返回路径给 Flutter。Flutter 只在需要显示时才解码图片到 GPU 纹理。
    *   **滑动窗口**：Rust 层只保留当前章节的分页索引在内存中。切换章节时，卸载旧章节的内存数据。

### 5. 可观测性与测试 (Observability & Testing)

既然你注重测试与可观测性：

#### **测试策略**
*   **Rust 层**：
    *   **单元测试**：针对分页算法的核心逻辑（如：给定 1000 字，行高 24，页高 800，应分为几页？）。
    *   **集成测试**：使用真实的 EPUB 文件，验证解析->分页->缓存的完整链路。
    *   **Mock Sled**：在测试中使用内存数据库替代 sled，加速测试。
*   **Flutter 层**：
    *   **Widget 测试**：验证 `EpubPageView` 是否正确响应 `Signal` 的变化。
    *   **Golden Test**：对比不同配置下的页面渲染截图，确保布局一致性。

#### **可观测性**
*   **性能指标**：
    *   在 Rust 层埋点：记录分页耗时、图片处理耗时、缓存命中率。
    *   通过 FRB 将这些指标暴露给 Flutter，或直接写入日志文件。
